Your AI has access. Who controls its actions?

MirrorGate sits between an AI agent and the tools it can use. Every proposed action must fit the approved task, the origin of the instruction and the data rules before it runs.

Three questions before any tool runs

The checks are plain code, not a language model’s opinion.

Is it part of the task?

Exporting data is not allowed when the task is preparing a payment draft.

Who asked for it?

An instruction found inside an invoice is untrusted. The employee’s request is not.

Do the rules pass?

Restricted data may only go to approved destinations, and large payments need a human.

The cases and the rules were written by the same team, so this shows the mechanism works, not how it performs on real attacks. MirrorGate’s two false positives are emails the invoice itself asked for. The agent is simulated, and decisions take under 0.001 ms because only the rules are timed.

What exists and what does not

Built in the prototype

  • Gate that holds the protected tools
  • Deterministic policy engine
  • SQLite audit log
  • 30 labelled test cases

Proposed, not built

  • FastAPI service and React dashboard
  • Real LLM agent
  • Process-level isolation, so the agent cannot reach tools directly
  • Larger test set written by other people
Compared against Microsoft Defender’s real-time protection for Copilot Studio agents, which checks each tool call before it runs (Microsoft Security Blog, 23 Jan 2026). We have not tested Defender. Whether task and instruction-origin checks add value over such guards is the question this project tests.

MirrorGate AI: trust the identity less, verify the action more.
